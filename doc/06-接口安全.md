# 接口安全

`security` 模块为 Spring MVC JSON 接口提供请求体解密、响应体加密和本机接口限流。默认协议是 `AES/CBC/PKCS5Padding + UTF-8 key + UTF-8 IV + 标准 Base64`；每种设备可以使用独立密钥，也可以单独切换为 AES-GCM。接口限流由 Caffeine 保存短期计数，不依赖 Spring Security、Redis 或 ORM。

阅读顺序：[完整配置](#完整主配置) · [接口限流](#接口限流) · [配置规则](#配置项与默认值) · [接口注解](#接口注解) · [CBC 前端对接](#默认-cbc-前端对接) · [排除路径](#明文排除路径) · [GCM](#可选-aes-gcm) · [手动 API](#手动使用) · [安全边界](#安全边界与限制)

## 引入模块

```xml
<dependency>
    <groupId>com.yulinlin</groupId>
    <artifactId>security</artifactId>
    <version>3.0</version>
</dependency>
```

模块不依赖 Spring Security，也不要求引入 ORM 或数据库驱动。引入后自动注册设备密钥管理器、请求解密 Advice、响应加密 Advice 和接口限流拦截器；多设备模式缺少 `unknown`、密钥或 CBC IV 时启动失败，不生成临时密钥，也不会静默退化成明文。

## 完整主配置

正式项目推荐使用多设备配置。下面完整展示设备请求头、未知设备兜底、明文路径、请求大小以及 Web、Android、iOS 独立密钥：

```yaml
yulinlin:
  security:
    crypto:
      # true：严格加密；false：兼容明文/密文请求，响应统一明文
      enabled: true

      # 客户端通过该请求头选择设备密钥
      device-header: Device-Type

      # 请求和响应都跳过加解密
      # 自定义该列表会替换默认值，因此需要保留 /monitor/**
      exclude-paths:
        - /monitor/**
        - /actuator/health
        - /public/**
        - /upload/**
        - /download/**

      # 同时限制收到的密文和解密后的 JSON
      max-request-size: 1MB

      devices:
        web:
          algorithm: AES/CBC/PKCS5Padding
          key: ${YULINLIN_SECURITY_WEB_KEY}
          iv: ${YULINLIN_SECURITY_WEB_IV}

        android:
          algorithm: AES/CBC/PKCS5Padding
          key: ${YULINLIN_SECURITY_ANDROID_KEY}
          iv: ${YULINLIN_SECURITY_ANDROID_IV}

        ios:
          algorithm: AES/CBC/PKCS5Padding
          key: ${YULINLIN_SECURITY_IOS_KEY}
          iv: ${YULINLIN_SECURITY_IOS_IV}

        # 固定保留名：请求头缺失、为空或未匹配任何设备时统一使用
        unknown:
          algorithm: AES/CBC/PKCS5Padding
          key: ${YULINLIN_SECURITY_UNKNOWN_KEY}
          iv: ${YULINLIN_SECURITY_UNKNOWN_IV}

    limit:
      enabled: true
      # 本机最多保留多少个“接口 + IP/设备 ID”计数器
      maximum-size: 50000
      ip-header: X-Real-IP
      device-id-header: Device-Id
      # 只有 TCP 连接来源属于这里时，框架才信任 ip-header
      trusted-proxies:
        - 127.0.0.1
        - "::1"
```

环境变量示例：

```properties
YULINLIN_SECURITY_WEB_KEY=MIGfMA0GCSqGSIb3
YULINLIN_SECURITY_WEB_IV=5efd3f6060e20765

YULINLIN_SECURITY_ANDROID_KEY=1234567890abcdef
YULINLIN_SECURITY_ANDROID_IV=abcdef1234567890

YULINLIN_SECURITY_IOS_KEY=fedcba0987654321
YULINLIN_SECURITY_IOS_IV=0123456789abcdef

YULINLIN_SECURITY_UNKNOWN_KEY=abcdef1234567890
YULINLIN_SECURITY_UNKNOWN_IV=1234567890abcdef
```

示例值仅用于说明长度。生产密钥必须由环境变量或密钥管理系统提供，不能提交到仓库。

## 接口限流

`@ApiLimit` 可以放在 Controller 类或方法上，方法配置覆盖类配置。默认同一客户端对同一接口每分钟最多调用 60 次，并按 IP 隔离：

```java
import com.yulinlin.security.annotation.ApiLimit;
import com.yulinlin.security.limit.LimitBy;

@RestController
public class VideoController {

    // 等价于 count=60、interval="1m"、by=LimitBy.IP
    @ApiLimit
    @PostMapping("/video/list")
    public R<?> list(@RequestBody VideoListPo request) {
        return R.ok(videoService.list(request));
    }

    // 设备 ID 缺失或非法时自动回退到真实 IP
    @ApiLimit(count = 20, interval = "10s", by = LimitBy.DEVICE)
    @PostMapping("/video/like")
    public R<?> like(@RequestBody VideoLikePo request) {
        return R.ok(videoService.like(request));
    }
}
```

支持 `500ms`、`10s`、`1m`、`1h` 等 Spring Duration 写法。没有 `@ApiLimit` 的接口不参与限流；`OPTIONS` 请求直接放行。超出限制时返回 HTTP `429`、`Retry-After` 响应头和未加密的统一 JSON：

```json
{
  "data": null,
  "code": 429,
  "crypt": false,
  "ok": false,
  "msg": "请求过于频繁，请稍后再试",
  "timestamp": 1792070400000
}
```

每条计数记录的 Key 是 `Controller 方法 + 限流维度 + IP/设备 ID`。Caffeine 根据该接口的 `interval` 淘汰不活跃记录，并用 `maximum-size` 防止大量随机 IP 或设备 ID 持续占用内存；未开启统计功能。达到容量上限而被提前淘汰的客户端再次访问时会重新计数。

### IP 黑名单

IP 黑名单由业务实现 `IpBlacklist` 接口，框架不规定数据来自内存、Caffeine、Redis 还是数据库。接口只接收已经完成可信代理检查并规范化的真实客户端 IP：

```java
import com.yulinlin.security.limit.IpBlacklist;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class SecurityConfiguration {

    @Bean
    public IpBlacklist ipBlacklist(IpBlacklistService service) {
        return service::isBlocked;
    }
}
```

一个简单的本地实现：

```java
import org.springframework.stereotype.Service;

import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

@Service
public class IpBlacklistService {
    private final Set<String> blockedIps = ConcurrentHashMap.newKeySet();

    public boolean isBlocked(String ip) {
        return blockedIps.contains(ip);
    }

    public void block(String ip) {
        blockedIps.add(ip);
    }

    public void unblock(String ip) {
        blockedIps.remove(ip);
    }
}
```

没有业务 Bean 时，框架注册默认空实现并放行所有 IP。命中黑名单时不进入 Controller，直接返回 HTTP `403` 和未加密的统一 JSON，`msg` 为 `当前 IP 已被禁止访问`。黑名单检查对所有 Controller 生效，不要求存在 `@ApiLimit`。

`isBlocked` 会在每次业务请求进入 Controller 前执行，不要在里面直接进行慢 SQL 查询。推荐使用内存集合、Caffeine、Redis Set，或者把数据库数据加载到本地后定时刷新。拉黑、解除、过期时间、CIDR 规则和管理接口都属于业务实现；框架只负责可靠传入真实 IP。实现抛出的异常不会被静默当作放行，避免安全检查在故障时无声失效。

### Nginx 真实 IP

后端由本机 Nginx 代理时推荐：

```nginx
location /api/ {
    if ($request_method = OPTIONS) {
        return 204;
    }

    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://127.0.0.1:9091;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

框架先检查 Java 服务看到的 TCP 来源地址。只有来源匹配 `trusted-proxies` 时才读取 `X-Real-IP`；否则忽略所有转发 IP，使用连接来源地址。缺失、非法或包含多个值的 `X-Real-IP` 也会回退连接地址，避免客户端伪造。`trusted-proxies` 支持单个 IPv4、IPv6 和 CIDR，例如容器网络可以明确增加 `172.16.0.0/12`，不要无条件信任所有地址。Java 服务端口也应只允许可信 Nginx 访问。

如果 Nginx 前面还有 CDN 或负载均衡，必须先正确配置 Nginx `real_ip` 模块，使 `$remote_addr` 恢复为真实客户端 IP，再转发给 Java。框架不会取 `X-Forwarded-For` 的第一个值。

`LimitBy.DEVICE` 读取 `Device-Id`，接受最长 128 个字符的字母、数字、点、下划线、冒号和短横线。设备 ID 由客户端提供，能够被修改或轮换，因此视频列表、详情和防采集接口应优先按 IP；设备维度适合点赞、收藏等正常设备行为的额度隔离，不能替代登录鉴权。

限流配置默认值：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 是否处理 `@ApiLimit` |
| `maximum-size` | `50000` | 本机同时保留的计数器上限，不是单接口请求次数 |
| `ip-header` | `X-Real-IP` | 仅从可信代理连接读取的客户端 IP 请求头 |
| `device-id-header` | `Device-Id` | `LimitBy.DEVICE` 使用的请求头 |
| `trusted-proxies` | `127.0.0.1`、`::1` | 可以提供真实 IP 请求头的代理地址或 CIDR |

## 登录用户模型

`security` 模块只定义最小登录用户协议，不规定用户表、登录流程、密码校验、Token 或权限实现。业务用户模型按需实现 `IUserDetails`：

```java
import com.yulinlin.security.auth.IUserDetails;

import java.util.Set;

public class LoginUser implements IUserDetails {
    private String userId;
    private String username;
    private Set<String> roles;
    private Set<String> permissions;
    private String tenantId;

    @Override
    public String getUserId() {
        return userId;
    }

    @Override
    public String getUsername() {
        return username;
    }

    @Override
    public Set<String> getRoles() {
        return roles;
    }

    @Override
    public Set<String> getPermissions() {
        return permissions;
    }

    @Override
    public Object getAttribute(String name) {
        return switch (name) {
            case "tenantId" -> tenantId;
            default -> null;
        };
    }
}
```

`roles` 和 `permissions` 使用 `Set` 表达唯一集合。接口自带 `hasRole(role)` 和 `hasPermission(permission)`，执行精确且区分大小写的集合判断；参数、角色集合或权限集合为 `null` 时返回 `false`。框架不自动增加 `ROLE_` 前缀，也不解释通配符。

```java
if (loginUser.hasRole("admin")) {
    // 当前用户具有 admin 角色
}

if (loginUser.hasPermission("video:update")) {
    // 当前用户可以修改视频
}
```

`getAttribute(name)` 只提供按名称读取，不暴露可修改的元数据 Map，也不强制业务使用 Map 存储。未知属性返回 `null`。

该模型不应包含密码、密码哈希、AES 密钥、Token、签发时间、过期时间、IP 或设备 ID。密码和 Token 属于认证凭证，IP 和设备属于单次登录或请求上下文，不属于用户本身。

### 安全管理器

业务项目实现 `ISecurityManager`，提供登录、注销、获取当前登录用户和强制刷新四个入口。框架只定义协议，不注册虚假的默认业务实现，也不规定账号保存在哪里：

```java
import com.yulinlin.security.auth.ISecurityManager;
import com.yulinlin.security.auth.IUserDetails;
import com.yulinlin.security.auth.LoginException;
import org.springframework.stereotype.Service;

@Service
public class SecurityManagerImpl implements ISecurityManager {

    @Override
    public IUserDetails login(String username, String password, String code) {
        IUserDetails user = authenticate(username, password, code);
        if (user == null) {
            throw new LoginException("用户名或密码错误");
        }
        return user;
    }

    @Override
    public void logout() {
        // 注销当前请求对应的用户
    }

    @Override
    public IUserDetails getUserDetails() {
        // 返回当前请求对应的登录用户；未登录返回 null
        return null;
    }

    @Override
    public IUserDetails getUserDetails(String userId) {
        // 读取指定用户，可以使用已有快照或缓存
        return findUser(userId);
    }

    @Override
    public IUserDetails refresh(String userId) {
        // 强制重新加载指定用户
        return reloadUser(userId);
    }
}
```

接口同时提供两种登录调用：

```java
securityManager.login(username, password);
securityManager.login(username, password, code);
```

两参数版本是默认方法，内部等价于 `login(username, password, null)`，用户只需要实现三参数版本。`code` 表示可选验证码；不使用验证码时为 `null`。

登录成功必须返回非空 `IUserDetails`。用户不存在、密码错误、验证码错误或账号状态拒绝登录时抛出 `LoginException`；数据库、Redis 等基础设施故障应保留原始异常，不应伪装成普通登录失败。用户名不存在和密码错误对外推荐使用相同提示，避免暴露账号是否存在。

`getUserDetails()` 读取当前请求的登录用户，未登录返回 `null`；`getUserDetails(userId)` 读取指定用户，可以使用已有登录快照或缓存，但不能改变当前请求身份：

```java
IUserDetails current = securityManager.getUserDetails();
IUserDetails specified = securityManager.getUserDetails("10001");
```

业务只需要实现 `refresh(String userId)`；无参数 `refresh()` 是默认方法，它先取得当前用户，再转调 `refresh(current.getUserId())`，未登录时返回 `null`：

```java
IUserDetails current = securityManager.refresh();
IUserDetails specified = securityManager.refresh("10001");
```

刷新用于重新加载最新角色、权限和扩展属性。传入其他用户 ID 时只刷新并返回该用户信息，不能把当前请求身份切换成该用户。刷新不等于重新输入密码登录，也不改变 Token 的签发时间和有效期。

## 配置项与默认值

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 是否启用严格加密；关闭后注解接口接受明文或密文，响应统一明文 |
| `device-header` | `Device-Type` | 客户端设备类型请求头；同时回写到加密响应 |
| `exclude-paths` | `/monitor/**` | 同时跳过请求解密和响应加密的 Spring 路径模式 |
| `max-request-size` | `1MB` | 密文与解密后正文的大小上限 |
| `devices.<name>.algorithm` | `AES/CBC/PKCS5Padding` | 当前设备的 AES 算法 |
| `devices.<name>.key` | 无 | 必填；CBC 接受 16、24 或 32 字节 |
| `devices.<name>.iv` | 无 | CBC 必填且必须是 16 字节 |
| `devices.<name>.key-encoding` | `UTF8` | 默认字符密钥不需要填写；GCM 示例使用 `BASE64` |
| `devices.<name>.iv-encoding` | `UTF8` | 默认字符 IV 不需要填写 |

配置中的设备名会去除首尾空白并转换为小写，只允许小写字母、数字、下划线和短横线，最大长度为 32。HTTP 请求未携带设备头、设备头为空、格式异常或设备名未配置时，统一使用保留设备 `devices.unknown`。`devices` 和 `devices.unknown` 都是必填项；框架不支持外层 `algorithm`、`key`、`iv`，也不需要 `default-device` 或额外的 fallback 属性。框架不自动暴露单设备 `AesCrypto` Bean，手动操作统一使用 `DeviceCryptoManager`。

CBC 参数必须满足：

```text
algorithm = AES/CBC/PKCS5Padding
key       = 16、24 或 32 字节
iv        = 16 字节
encoding  = UTF-8
cipher    = 标准 Base64
padding   = PKCS5/PKCS7
```

建议 key 和 IV 使用 ASCII 字符，避免中文 UTF-8 字符占多个字节。Java 的 `PKCS5Padding` 与常见 JavaScript AES 实现的 `Pkcs7` 在 AES 分组下兼容。

## 接口注解

需要加密的业务接口使用 `@ApiCrypto`。它可以放在 Controller 类或具体方法上，方法配置优先于类配置。全局 `enabled` 控制严格加密模式，但不会删除请求解密能力：

| 全局配置 | 接口注解 | 请求 | 响应 |
| --- | --- | --- | --- |
| `enabled=true` | `@ApiCrypto` / `@ApiCrypto(true)` | 必须传整个 JSON 加密后的 Base64 密文 | 加密 |
| `enabled=true` | `@ApiCrypto(false)` | 普通 JSON 原样读取；非 JSON body 仍尝试解密 | 明文 |
| `enabled=false` | `@ApiCrypto(true/false)` | 普通 JSON 或整个 body 密文都支持 | 明文 |
| 任意值 | 没有注解 | security 完全不处理 | 明文 |
| 任意值 | 命中 `exclude-paths` | security 完全不处理 | 明文 |

`enabled=false` 是兼容模式，不是卸载安全模块。设备密钥管理器和请求 Advice 仍会注册，key 与 IV 仍然必须配置，以便继续解密尚未升级的旧客户端；此时 `@ApiCrypto(true)` 不再拒绝明文请求，响应也不会加密。已经发送密文的客户端和已经切换明文的客户端可以并行迁移。

业务 JSON 接口推荐统一使用 `@PostMapping + @RequestBody`。请求 Advice 只处理 body，不加密 query 参数和 path 变量。

```java
package demo.api;

import com.yulinlin.security.annotation.ApiCrypto;
import com.yulinlin.starter.domain.R;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class UserController {

    @ApiCrypto
    @PostMapping("/api/user/detail")
    public R<UserVO> detail(@RequestBody UserDetailPo request) {
        return R.ok(userService.detail(request.getId()));
    }

    @ApiCrypto(false)
    @PostMapping("/api/user/public-detail")
    public R<UserVO> publicDetail(@RequestBody UserDetailPo request) {
        return R.ok(userService.detail(request.getId()));
    }
}
```

`@ApiCrypto(false)` 是兼容模式，不是完全关闭请求处理。框架把 body 转成 UTF-8 字符串：忽略首尾空白判断后，以 `{` 或 `[` 开头时直接交给 Jackson；其他内容按当前设备的 Base64 密文解密。它不会为了判断明文而预解析 JSON，因此明文请求只反序列化一次。错误 Base64 或解密失败返回 400，不会再次降级为明文。

### 响应加密规则

- 普通 Java 对象：整个对象序列化后加密，响应 JSON 是一个 Base64 字符串。
- `R<E>`：只加密非 null 的 `data`，保留 `code`、`msg`、`ok` 和 `timestamp`，并设置 `crypt=true`。
- 返回值或 `R.data` 是 `String` 时，直接加密该字符串的 UTF-8 字节，不先增加 JSON 双引号；其他类型仍先序列化为 JSON。
- `R.data == null`：不生成无意义密文，`crypt` 保持 `false`。
- `ResponseVo<E>`：仅保留废弃兼容，行为与 `R<E>` 相同。

因此客户端必须按接口约定选择解密方法：字符串使用 `decryptText()`，对象、集合、数字和布尔值使用 `decryptJson()`。密文自身不能可靠判断原始 Java 类型。

`R<E>` 加密响应示例：

```json
{
  "code": 200,
  "msg": "操作成功",
  "ok": true,
  "crypt": true,
  "data": "mFbzvANmZJZQj/3nB4zKpA==",
  "timestamp": 1792070400000
}
```

## 默认 CBC 前端对接

请求仍使用 `Content-Type: application/json`。推荐 body 直接发送未经 JSON 双引号包裹的标准 Base64 密文；为兼容浏览器请求链路，服务端也接受 Axios 添加一层 JSON 双引号、`+` 被表单处理转换为空格，以及密文中混入回车、换行或制表符的情况：

```http
POST /api/user/detail HTTP/1.1
Content-Type: application/json
Device-Type: web

N4H0Qf4H0m4YqQPG4Q3XWg==
```

以下 Axios 实际报文也能兼容，服务端会先移除最外层双引号再进行 Base64 解码：

```text
"N4H0Qf4H0m4YqQPG4Q3XWg=="
```

服务端加密响应会返回实际设备和算法：

```http
Device-Type: web
X-Yulinlin-Crypto: AES/CBC/PKCS5Padding
```

下面使用浏览器原生 Web Crypto API，与默认 CBC、UTF-8 key/IV 和标准 Base64 对齐。Web Crypto 的 AES-CBC 使用 PKCS7 填充，与服务端 `PKCS5Padding` 兼容：

```javascript
const encoder = new TextEncoder();
const decoder = new TextDecoder();

function bytesToBase64(bytes) {
  let binary = "";
  for (const value of new Uint8Array(bytes)) binary += String.fromCharCode(value);
  return btoa(binary);
}

function base64ToBytes(value) {
  return Uint8Array.from(atob(value), char => char.charCodeAt(0));
}

async function importCbcKey(keyText) {
  const bytes = encoder.encode(keyText);
  if (![16, 24, 32].includes(bytes.length)) throw new Error("AES key length is invalid");
  return crypto.subtle.importKey("raw", bytes, {name: "AES-CBC"}, false,
      ["encrypt", "decrypt"]);
}

function cbcIv(ivText) {
  const bytes = encoder.encode(ivText);
  if (bytes.length !== 16) throw new Error("AES-CBC IV must contain 16 bytes");
  return bytes;
}

async function encryptJson(value, keyText, ivText) {
  const key = await importCbcKey(keyText);
  const encrypted = await crypto.subtle.encrypt(
      {name: "AES-CBC", iv: cbcIv(ivText)},
      key,
      encoder.encode(JSON.stringify(value)));
  return bytesToBase64(encrypted);
}

async function decryptText(ciphertext, keyText, ivText) {
  const key = await importCbcKey(keyText);
  const plaintext = await crypto.subtle.decrypt(
      {name: "AES-CBC", iv: cbcIv(ivText)},
      key,
      base64ToBytes(ciphertext.trim()));
  return decoder.decode(plaintext);
}

async function decryptJson(ciphertext, keyText, ivText) {
  return JSON.parse(await decryptText(ciphertext, keyText, ivText));
}

const deviceType = "web";
const key = "MIGfMA0GCSqGSIb3";
const iv = "5efd3f6060e20765";
const body = await encryptJson({id: "U1001"}, key, iv);

const response = await fetch("/api/user/detail", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Device-Type": deviceType
  },
  body
});

const responseBody = await response.json();
const result = responseBody?.crypt === true
    ? {...responseBody, data: await decryptJson(responseBody.data, key, iv)}
    : typeof responseBody === "string"
        ? await decryptText(responseBody, key, iv)
        : responseBody;
```

上例接口返回的是 `R<UserVO>`，所以 `data` 使用 `decryptJson()`；如果接口返回 `R<String>`，对应代码应改为：

```javascript
const result = responseBody?.crypt === true
    ? {...responseBody, data: await decryptText(responseBody.data, key, iv)}
    : responseBody;
```

跨域调用时，业务 CORS 配置必须允许请求头 `Device-Type`，并暴露响应头 `Device-Type` 和 `X-Yulinlin-Crypto`。密钥不得直接硬编码在公开源码中；上述浏览器代码只用于说明协议对接。

## 多设备选择

请求头决定当前使用哪组设备密钥：

```http
Device-Type: web
Device-Type: android
Device-Type: ios
```

| 请求头 | 最终设备 |
| --- | --- |
| 缺失或空值 | `unknown` |
| `web`、`android` 等已配置名称 | 对应设备 |
| 未配置的名称 | `unknown` |
| 不符合设备名格式的值 | `unknown` |

设备名匹配不区分大小写并忽略首尾空白。响应回写实际解析后的设备类型，客户端应优先读取响应 `Device-Type`，再选择对应密钥解密。设备请求头只负责选密钥，不是身份认证信息，不能仅凭该值判断调用方可信。

## 明文排除路径

`exclude-paths` 是服务端控制的完整排除列表，支持 Spring 路径模式。命中后，即使接口存在 `@ApiCrypto(true)`，请求体也不解密，响应体也不加密：

```yaml
yulinlin:
  security:
    crypto:
      exclude-paths:
        - /monitor/**
        - /actuator/health
        - /public/**
```

默认列表只有 `/monitor/**`。配置新列表会替换默认列表，因此使用监控模块时必须继续保留它。不要提供由客户端控制的“跳过加密”请求头，否则业务接口可能被绕过。

文件上传、文件下载、视频流、SSE、WebSocket、静态资源和健康检查不适合 JSON 加密 Advice，应保持无 `@ApiCrypto`，必要时加入排除路径。

## 可选 AES-GCM

支付、订单等需要密文完整性校验的设备可以显式切换到 GCM：

```yaml
yulinlin:
  security:
    crypto:
      devices:
        web:
          key: ${YULINLIN_SECURITY_WEB_KEY}
          iv: ${YULINLIN_SECURITY_WEB_IV}
        ios:
          algorithm: AES/GCM/NoPadding
          key-encoding: BASE64
          key: ${YULINLIN_SECURITY_IOS_KEY}
        unknown:
          key: ${YULINLIN_SECURITY_UNKNOWN_KEY}
          iv: ${YULINLIN_SECURITY_UNKNOWN_IV}
```

GCM 要求 Base64 解码后恰好为 32 字节的密钥，不允许配置固定 `iv`。框架每次生成 12 字节随机 IV，Base64 解码后的报文结构为：

```text
12字节随机IV + 密文 + 16字节认证标签
```

GCM 使用以下 UTF-8 内容作为 AAD，客户端必须完全一致：

```text
1\n<规范化设备类型>\nA256GCM
```

例如 web 设备的 AAD 是 `1\nweb\nA256GCM`。密文、设备名、IV、认证标签或密钥不匹配都会导致解密失败；这是 GCM 相比默认固定 IV CBC 的主要安全优势。

## 手动使用

需要显式选择设备时，注入线程安全的 `DeviceCryptoManager`：

```java
import com.yulinlin.security.crypto.DeviceCryptoManager;

public class SecureValueService {
    private final DeviceCryptoManager cryptoManager;

    public SecureValueService(DeviceCryptoManager cryptoManager) {
        this.cryptoManager = cryptoManager;
    }

    public String encrypt(String deviceType, String value) {
        return cryptoManager.getRequired(deviceType).encryptBase64(value);
    }

    public String decrypt(String deviceType, String ciphertext) {
        return cryptoManager.getRequired(deviceType).decryptBase64ToString(ciphertext);
    }
}
```

框架不会自动注入单设备 `AesCrypto`，避免多设备项目误用固定密钥。脱离 Spring、明确只处理一种密钥时，仍可以直接创建底层实现：

```java
AesCrypto cbc = new AesCbcCrypto(keyBytes, ivBytes);
AesCrypto gcm = new AesGcmCrypto(keyBytes, "web");
```

实现每次操作创建独立 `Cipher`，可以被多个请求线程共享。

## 安全边界与限制

- 当前只支持 Spring MVC，不支持 WebFlux。
- 生产环境仍必须使用 HTTPS；接口加密不能替代 TLS。
- CBC 使用固定 IV，不能可靠发现密文篡改；高敏感业务选择 GCM。
- 浏览器必须持有共享 AES 密钥，因此网页脚本、浏览器扩展和自动化浏览器最终都能读取它。该能力只能提高普通采集脚本的成本，不能单独承担防爬虫职责。
- AES 不是密码哈希，用户密码必须使用专用密码哈希算法保存。
- 自动 Advice 只适合 JSON 请求和 JSON/字符串响应，不适合 multipart、文件流、视频流、SSE 或 WebSocket。
- 日志不得记录密钥、IV、解密后的敏感正文或完整密文。
- 当前没有实现时间戳、nonce 防重放和密钥轮换，业务不能假设已经具备这些能力。
- 当前限流状态只存于单个 Java 进程；多实例部署时每个实例独立计数，不提供分布式强一致限流。
- 设备 ID 可以伪造，IP 也可能由 NAT 共享；限流用于控制接口频率，不能单独判断用户一定是爬虫。
