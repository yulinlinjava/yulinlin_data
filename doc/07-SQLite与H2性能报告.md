# SQLite/H2 多线程写入性能报告

本报告记录 yulinlin-data 在本地文件数据库上的完整 ORM 写入性能。它回答的是：在“多个业务线程持续提交小批量数据”的调用方式下，SQLite 与 H2 应如何选择。它不是数据库原生 JDBC 极限测试，也不代表所有硬件、事务和持久化配置下的绝对排名。

阅读导航：[结论](#结论先行) · [业务模型](#业务模型) · [测试口径](#测试口径) · [正式结果](#正式结果) · [结果分析](#结果分析) · [选型建议](#选型建议) · [复现](#复现方法) · [限制](#限制与后续验证)

测试日期：2026-10-06。代码基线：制品版本 3.0、JDK 25。

## 结论先行

| 方案 | 10 万行平均耗时 | 吞吐量 | 每批累计分配 | 适合场景 |
| --- | ---: | ---: | ---: | --- |
| H2：4 业务线程、4 连接 | **1.119 秒** | **89,401 行/秒** | 3.497 GB | 多线程、小批量、吞吐优先 |
| SQLite：4 业务线程、1 连接 | 2.200 秒 | 45,456 行/秒 | **1.980 GB** | 单文件、写入可排队、内存分配优先 |

在本次模型中，H2 相对 SQLite 耗时降低约 49.2%，吞吐量提高约 96.7%；SQLite 每批累计分配量低约 43.4%。外层已经并发提交时，单个请求不要再调用框架 `.batch()`。

## 业务模型

- 总写入量：100,000 行。
- 业务线程：4 个长期存活线程。
- 单次 ORM 请求：最多 128 个对象。
- 请求数量：782 个，其中 781 个请求为 128 行，最后一个为 32 行。
- 请求按轮询分配给 4 个线程；每个线程串行处理分配给自己的请求。
- 每个请求独立开启并提交事务，10 万行整体不是一个原子事务。
- 不调用框架内部 `.batch()`，避免业务线程内再次拆分异步任务和连接。
- SQLite 使用 1 个物理连接；H2 最多使用 4 个连接。

JMH 显示的 `Threads: 1` 是基准协调线程。一次 benchmark 调用内部会把 782 个请求交给 4 个真实业务线程，因此不表示业务只有一个线程。

### 测试数据

每行包含 6 个字段：字符串主键、租户整数、序号长整数、BigDecimal 金额、普通字符串载荷和 Date 时间。表上声明 `tenantId + createdAt` 普通联合索引，写入时间包含 ORM 字段读取、公共编码器、SQL 解析、参数绑定、JDBC batch、索引维护、事务提交以及 4 个业务任务的调度与汇总。

## 测试口径

### 运行环境

| 项目 | 值 |
| --- | --- |
| 操作系统 | Windows 11 |
| JVM | OpenJDK 64-Bit Server VM 25+36-3489 |
| JMH | 1.37 |
| 模式 | AverageTime，单位 ms/op |
| Fork | 1 |
| 预热 | 2 轮，每轮 1 秒 |
| 正式采样 | 5 轮，每轮 1 秒 |
| JVM 参数 | `-Xms512m -Xmx2g --enable-native-access=ALL-UNNAMED` |
| Profiler | JMH `gc` |
| 硬件 | 本次原始记录未保存 CPU、内存和磁盘型号 |

一次 `op` 表示完整写入并等待 100,000 行结束，不是写入一行。吞吐量按 `100000 / (ms/op / 1000)` 换算；单行耗时和分配量只是整批结果的均摊值，不代表单行独立事务的延迟。

### 数据库与框架参数

| 参数 | SQLite | H2 |
| --- | --- | --- |
| 存储方式 | 临时目录中的文件数据库 | 临时目录中的文件数据库 |
| 模式 | WAL，`synchronous=NORMAL` | `MODE=MYSQL` |
| 连接数 | 固定 1 | 最多 4 |
| 等锁/连接设置 | `busy-timeout=5000` | 默认连接超时，`auto-server=false` |
| Schema | 配置扫描包，启动时创建表和联合索引 | `schema-mode=CREATE` + 扫描包，启动时创建 |
| JDBC batch 上限 | 256 | 256 |
| 单次请求行数 | 最大 128 | 最大 128 |

由于请求最多 128 行，小于 256 行的 JDBC batch 上限，所以每个 ORM 请求只执行一次 `PreparedStatement.executeBatch()`。公共并行连接配置为 4，但 SQLite Session 明确不支持多连接并行写入，因此不会把请求再次拆成多连接任务。

### 计时边界

计入分数：

- 4 个业务任务的提交、调度、等待与结果汇总；
- 每个请求的完整 ModelInsertWrapper/RouteSession/Session 路径；
- 对象字段读取、类型编码、SQL 与参数生成；
- 获取连接、JDBC batch、数据库写入、索引维护和事务提交。

不计入分数：

- Spring 上下文启动和线程池创建；
- 100,000 个对象的创建与请求分组；
- 临时数据库目录和文件创建；
- 应用启动阶段的建表、建索引；
- 每轮开始前的清表；
- 每轮结束后的总行数查询与校验。

每次正式调用结束后都断言表中恰好存在 100,000 行；返回的 JDBC 更新计数也必须等于 100,000，否则本轮直接失败。

## 正式结果

### 耗时与吞吐量

| 场景 | 平均耗时 | JMH 误差（99.9%） | 最小值 | 最大值 | 标准差 | 吞吐量 | 单行均摊 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| H2：4 线程、4 连接 | **1,118.556 ms** | ±259.345 ms | 1,067.291 ms | 1,233.788 ms | 67.351 ms | **89,401 行/秒** | **11.186 μs** |
| SQLite：4 线程、1 连接 | 2,199.920 ms | ±1,209.437 ms | 1,961.854 ms | 2,746.010 ms | 314.087 ms | 45,456 行/秒 | 21.999 μs |

JMH 误差是 5 个样本推算的 99.9% 置信区间半宽；本次只有 1 个 fork、5 个正式样本，所以它很宽。选型应结合差距、原始样本和数据库并发模型，不能只看置信区间。

正式耗时样本，单位为 ms/10 万行：

| 方案 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 | 第 5 轮 |
| --- | ---: | ---: | ---: | ---: | ---: |
| H2 | 1,233.788 | 1,098.787 | 1,117.323 | 1,075.594 | 1,067.291 |
| SQLite | 2,045.416 | 1,961.854 | 2,078.120 | 2,168.199 | 2,746.010 |

### 分配与 GC

| 场景 | 分配速率 | 每批累计分配 | 单行均摊分配 | 5 轮 GC 次数 | 5 轮 GC 时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| H2 | 2,785.858 MB/s | 3,496,897,299 B | 34.15 KiB | 35 | 177 ms |
| SQLite | 863.227 MB/s | 1,979,772,952 B | 19.33 KiB | 31 | 58 ms |

“每批累计分配”是一次操作期间所有临时对象分配量的累计，不是峰值堆占用，也不表示进程同时占用数 GB 内存。GC 次数和时间是 5 个正式采样的总和，不是单次操作值。

## 结果分析

1. H2 在当前业务模型中更快。4 个连接可以同时处理不同的 128 行请求，覆盖一部分事务提交、SQL 处理与文件等待时间。
2. SQLite 的单写连接会让 4 个业务线程的写事务排队。WAL 可以改善读写并发，但不能让同一个 SQLite 文件同时执行多个写事务。
3. H2 的正式样本更稳定；SQLite 第 5 轮升至 2.746 秒，导致标准差和 JMH 误差明显增大。仅凭本轮数据不能判断抖动来自文件系统、锁等待、缓存或系统后台负载。
4. SQLite 的分配效率更好。H2 的累计分配量比 SQLite 高约 76.6%，说明后续若继续优化 H2 路径，应优先分析编码、参数容器、SQL 节点和驱动内部对象。
5. 结果衡量的是框架完整 ORM 路径。它适合回答项目选型问题，不适合代替原生 JDBC、数据库引擎或其他 ORM 的横向基准。

## 选型建议

| 需求 | 建议 |
| --- | --- |
| 多线程持续提交 128 行以内的小批次，追求写入吞吐 | 选择 H2；连接上限先与业务写线程数一致，当前默认 4 |
| 单文件部署、配置简单、写流量不高或允许排队 | 选择 SQLite WAL |
| 更关注较低临时对象分配 | 本次结果中 SQLite 更合适 |
| 要求整个 10 万行导入原子提交 | 当前 782 个独立事务模型不满足；改为单事务方案后重新测试 |
| 要求单连接事务内严格“读己之写” | H2 设置 `parallel-connections: 1`，并按单连接模型重新测试 |

使用时还应遵守：

- 外层已有 4 个业务线程时，128 行请求不要再调用 `.batch()`，否则会形成嵌套并发并放大连接占用。
- 不要盲目把 H2 连接数调得高于实际业务线程数；更多连接会增加锁竞争、内存和调度成本。
- SQLite 多线程调用仍然可以保证线程安全地排队执行，但不能据此期待多写吞吐线性提升；高压写入可在业务层使用有界队列和单写线程形成背压。
- SQLite WAL/NORMAL 与 H2 文件模式的落盘策略并不完全等价。对断电持久性有严格要求时，应先统一持久化级别，再重新比较。

## 复现方法

基准源码：[LocalDatabaseWriteBenchmark.java](../admin/src/jmh/java/com/yulinlin/admin/benchmark/LocalDatabaseWriteBenchmark.java)。运行脚本：[run-local-db-benchmark.ps1](../admin/run-local-db-benchmark.ps1)。在仓库根目录使用 JDK 25 执行：

```powershell
./admin/run-local-db-benchmark.ps1
```

显式指定本报告参数：

```powershell
./admin/run-local-db-benchmark.ps1 `
  -Size 100000 `
  -BusinessThreads 4 `
  -RequestSize 128 `
  -Forks 1 `
  -Warmups 2 `
  -Iterations 5 `
  -Duration 1s `
  -MaxHeap 2g
```

脚本先用 `-Dmaven.test.skip=true -Plocal-db-benchmark` 打包专用 benchmark JAR，再运行 JMH；它不会执行普通单元测试。文本与 JSON 原始结果写入：

```text
admin/target/local-db-jmh/sqlite-h2-business-threads.log
admin/target/local-db-jmh/sqlite-h2-business-threads.json
```

每次正式报告至少保留测试日期、代码提交、JDK、操作系统、CPU、内存、磁盘、文件系统、参数、日志和 JSON。修改线程数、连接数、批次或持久化设置后，不应继续引用本报告数字。

## 限制与后续验证

- 本轮未记录硬件型号，也没有隔离杀毒软件、系统文件缓存、CPU 电源策略和后台负载。
- 只有 1 个 fork、5 个正式样本，适合当前工程的初步选型，不是严谨的跨机器容量结论。
- 只测试了 4 线程、128 行请求、10 万行这一组参数，没有覆盖 1/2/8 线程及 1/32/256 行请求。
- 没有原生 JDBC 基线，因此不能将 ORM 分配量全部归因于框架或驱动。
- 两组清表操作位于计时区间外，但 H2 使用 TRUNCATE、SQLite 使用 DELETE；数据库文件页复用和系统缓存仍可能影响下一轮写入。
- SQLite NORMAL 与 H2 默认文件持久化语义不同，性能优势不能直接等同于相同故障恢复能力下的优势。
- JMH 1.37 在 JDK 25 输出了 `sun.misc.Unsafe` 终止弃用警告；本次运行成功，但升级 JDK/JMH 后应重新验证结果。

若要形成发布级容量结论，建议至少使用 3 个 fork，记录硬件，固定系统负载，并补充线程数 × 请求大小的参数矩阵、等持久化级别对比、原生 JDBC 基线和 JFR/async-profiler 分配热点分析。
