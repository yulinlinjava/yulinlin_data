# 核心组件与业务边界（内部开发）

面向框架维护者和修改源码的 AI，以 RouteSession 为主线说明当前组件、调用顺序与职责边界。本文是这些架构规则的唯一维护源；新数据源开发步骤、编解码扩展和排障流程见[扩展开发与维护](05-扩展开发与维护.md)。业务使用看对应使用专题，不将内部接口当作独立业务入口。

## 架构与职责

core 是统一的数据访问与执行协调层。业务入口是 `RouteSession`，不是各数据库 Session；但不能把 RouteSession 理解为所有功能的具体实现。以下描述对应当前源码，供维护者和修改框架的 AI 定位职责。

```text
业务 → Model / Wrapper → INode → QueryRequest / ExecuteRequest
  → RouteSession：初选节点 → before → 按最终请求调整路由
  → EntitySession / AbstractSession：公共执行流程
      → ParseManager + 编码 Buffer → SQL / SDK 请求
      → 查询缓存命中，或调用数据库执行器 → 解码为实体
      → 查询结果关联加载、代理增强
  → RouteSession：after → 返回

写入事务由 RouteSession → TransactionListenerManager 协调；
实际连接、SQL / DSL 和驱动行为由数据库模块负责。
```

| 层 | 职责 | 不应承担 |
| --- | --- | --- |
| Model/Wrapper/IWrapperFactory | 链式 API、实体与条件对象转操作节点 | 获取连接、执行数据库操作 |
| anno/node/alias/util | 表、字段、条件、关联、排序和聚合的通用元数据与节点 | 绑定数据库专属语法 |
| BaseRequest/QueryRequest/ExecuteRequest | 携带节点、fromClass、结果类型、group、缓存、批量和队列选项；便利方法委托 SessionUtil.route() | 独立管理连接或物理事务 |
| ParseManager/IParse | 节点注册、生成 SQL/SDK 请求 | 借连接或提交事务 |
| CoderManager/IDataBuffer | Java 与后端值转换 | 选库和连接池治理 |
| EntitySession | 数据源执行、资源事务及 Schema 协议 | 承诺所有后端都支持相同事务、并发或建表能力 |
| AbstractSession | 公共查询/分页/批量流程、查询缓存、解码、结果增强、计时和监听通知 | 执行路由过滤器、独立开启业务事务、反向调用事务管理器 |
| 具体 Session | SQL/SDK 执行、参数绑定、读取、本数据源连接资源和日志格式 | 复制没有差异的公共 CRUD 流程 |
| SessionFactory | 创建 Session，初始化缓存、编码器、解析器、代理服务、可选执行监听器、配置和 group | 默认承担路由注册或建表；注册日志管理器 |
| RouteSession | 唯一业务 CRUD 入口、过滤器、会话选择、事务协调、队列接入与写后缓存失效决策 | 持有另一份事务上下文、翻译方言、执行物理 commit 或实现 XA |
| IFilterManager/SimpFilterManager | 注册、排序、匹配、顺序执行过滤器 | 选择数据源、执行 SQL 或管理事务 |
| TransactionListenerManager | 统一业务上下文、嵌套深度、代理写回、资源完成与回调 | 直接操作 JDBC Connection 或实现 XA |
| JdbcTransactionResources（jdbc 模块） | 单个 Session 事务内的连接借还、按需扩容、物理提交/回滚与释放 | 全局连接池、业务事务嵌套、路由或 Spring 连接归属判断 |
| RegisterSession/LoadBalance | Session 注册、选库作用域、默认组、cluster 和权重选择 | 数据源 URL 校验、执行 CRUD 或保证事务一致性 |
| EntityProxyService/EntityProxyFactory | 关联加载、同步代理生成与脏字段记录 | 再维护一套事务 ThreadLocal 或自行提交连接 |
| WriteQueueManager | 延迟接收节点、触发刷新、分组和重试调度 | 持久化消息、分布式队列、自动推断业务聚合语义 |
| EntityCounterManager / CounterUpdate / CounterInsert（common） | 链式或模型按主键聚合更新，或按非数字维度聚合插入；提交快照、数字求和、定时刷新与失败批次保留 | 分布式统计、严格分钟窗口、exactly-once；不能绕过 RouteSession |
| cache-core | 缓存 SPI、CacheRegistry 注册/默认选择、CacheClient 命名路由、Key/TTL 与 namespace/partition 模型 | 解析 INode、Wrapper 或数据库表注解；自动串联多个 Provider |
| core/cache | ORM 查询 Key 构造、表依赖解析和写后失效决策 | 实现 Caffeine、Ehcache 或 Redis 存储 |
| SchemaEntityScanner | 包扫描和结构拥有者校验 | 生成各数据库 DDL、在每次 CRUD 前建表 |
| SchemaManager / SchemaColumnAlter（jdbc） | 数据库元数据与 DDL；显式开启 alter-column-type 且 CREATE 时受限改类型/扩容，执行委托所属 Session | 自动确认业务数据可转换、删约束促成转换、跨表原子迁移或数据补偿 |
| SchemaErrors（jdbc） | 统一中文结构诊断、原因和处理建议；包装失败 DDL，保留驱动异常链及错误码 | 决定兼容性、执行 SQL、自动修复结构或吞掉异常 |
| SyncRequestFilter / SyncManager（data-sync） | 匹配源组和实体、保存节点快照、afterCommit 入队、顺序消费、失败暂停及全量维护保护 | CDC、源事务 Outbox、自动对账、分布式一致性 |
| DataSyncClient / JdbcFullSyncJob（data-sync） | MySQL/PostgreSQL 单表主键分页复制、目标本地检查点续传、中文进度 | 普通业务 CRUD、在线快照、目标额外行删除、可靠增量交付 |
| SessionExecution/SessionExecutionListener | 单次数据源执行结果、可选监控扩展点 | 判断事务提交成功、实现监控页面或反向修改请求 |
| AOP/YulinlinCoreAutoConfig | 注解入口与组件装配 | 实现订单、权限等业务规则 |
| ISecurityManager / SecurityUtil / SecurityContext（security） | 唯一登录管理器、静态委托入口与线程身份；业务校验后 login(userId, deviceType) 返回 LoginResult，resolveSession 恢复 LoginSession | 校验账号密码/验证码、强制账号表结构、多实现同时登录、跨线程继承身份 |
| UserStore（security） | 业务 Bean 按 userId 加载安全用户、角色和权限，缺失/禁用时拒绝登录 | 生成 Token、维护登录记录、把凭证带入用户 DTO |
| JwtTokenCodec / JwtSessionStore（security-jwt） | 分别负责签发/验签和按 tokenId 保存/读取/撤销记录；Store 支持 getByUserId 和默认 removeByUserId，Caffeine 按需遍历；替换 Bean 时默认实现退让 | 存储层管理线程身份、吞掉故障或丢记录后纯 JWT 放行；将用户批量撤销视为并发登录的原子屏障 |
| SaTokenSecurityManager（security-sa-token） | 委托 Sa-Token 生命周期与存储，复用 UserStore 和公共上下文；与 JWT 模块二选一 | 再建一份 JWT 登录存储、混用两套登录管理器 |
| LoginContextInterceptor / ApiAuthAspect（security） | 拦截器恢复/清理身份，AOP 通过 ISecurityManager 校验登录/角色/权限 | 重复执行两套权限注解逻辑、替代会话存储或外部安全框架 |
| core/http | 独立 HTTP 客户端工具 | 参与 ORM 路由、事务或数据库监听链 |

业务 CRUD 必须经过 RouteSession，Model Wrapper、Request 便利方法和事务切面均接入这一入口。具体 Session 是执行器和资源参与者，不作为独立业务事务入口；建表 SQL 预览、启动 Schema 初始化和解析器专项用例仍可以直接使用其底层能力。

启动 Schema 的 `alter-column-type` 默认关闭，放在 JdbcSessionProperties，由各数据库配置前缀独立绑定。MySQL/PostgreSQL/H2 在初始化时读取实际元数据、检查主键/生成列/外键等限制，再生成改列 SQL；Session 负责连接、DDL 日志和异常传播。VALIDATE 永远不修改，SQLite 不提供自动改类型。默认值和索引无法由数据库安全保留时停止启动，不自动删除重建；多条 DDL 不保证整体回滚，具体限制与人工备份要求见[改列说明](01-接入与数据源.md#显式允许修改列类型)。

结构诊断按本次 SchemaMode 与改列开关给出建议：VALIDATE 只校验，主键/索引冲突须人工处理，SQLite 不支持自动改类型。Session 保留 DDL 日志职责，SchemaErrors 只负责诊断文本。不要将驱动原始错误强行翻译或丢弃，也不要将 DDL 失败描述为“已全部回滚”；使用规则见[表结构错误排查](01-接入与数据源.md#表结构错误排查)。

## RouteSession 执行链

**同步重放例外入口：** `replayWrite(targetGroup, request)` 仅供内部适配器重放已经完成业务加工的节点。强制明确目标组及 master，不走 before/after、不进入普通延迟队列，因此不重复改表名、补默认值，也不会触发下一层同步。仍由 executeNow 管理事务参与、缓存失效和具体 Session 执行/日志。普通业务 CRUD 不应调用此入口绕过过滤器，目标权限及租户隔离必须由同步配置保证。

**增量通知：** data-sync 的写后过滤器在源事务内保存独立快照，登记 TransactionUtil.afterCommit；最外层成功后才入队。队列后台真正写入和代理提交前 flush 产生的请求同样走此链路。每个请求在目标独立提交，不保留源多请求事务的原子性；失败任务不越过、不自动重试。内存容量按节点计，快照/入队失败显式暂停并报告可能缺口，不能回滚已提交的源数据。SyncTaskStore 内置没有持久化队列恢复或原子源事件记录。

**全量维护例外入口：** DataSyncClient.sync(source,target,class) 通过 RouteSession 选择 master，再借 JdbcSession 独立维护连接，不加入业务事务、不走业务过滤器或代理。FullSyncMapping 校验单表实体与实际单列主键；JdbcFullSyncJob 复用源/目标各自 CoderManager 和 Session 读取/绑定策略。每批目标业务行与 yulinlin_sync_progress 检查点同连接提交，确认成功后调用 RouteSession.invalidateMaintenanceCache 清理目标命名空间。sync 自动续传；restart 重置该任务进度，不清空目标。禁止在业务事务中调用，不能把维护连接能力用于普通 CRUD 绕开 RouteSession。

**全量/增量衔接：** 当前采用轻量方案，日常增量正常运行，全量只由人工在维护窗口调用；空规则也可仅提供人工 API。启动入口 SyncManager.start(groups) 只校验组并调度增量，不接收全量执行器，不扫描实体。启动自动全量开关和相关执行器已移除；人工全量保留独立入口，不自动协调停写。

ManualGuard 对本进程所有写向目标 group 的规则提供维护保护：进入前要求空闲且无积压/暂停，未满足直接拒绝，不等待排空；全量期间停止调度，退出时恢复正常规则调度，但不解除错误暂停。它不会阻止源业务提交或停止其他实例；业务必须先停写、结束在途事务并排空后台写任务及增量，成功核对后再恢复写入。普通全量失败也会释放维护保护，所以调用方必须继续保持停写以便续传；检测冲突时需人工修复，不能自动重放可能重复的 inc/dec。持久化检查点只属于全量任务，不等于增量已具备可靠投递；提交结果不确定时仅更新错误状态，不用内存中的旧游标覆盖数据库进度。

**查询：** `RouteSession.executeList` 应用实体路由、初选 Session、执行 before；过滤器可以改表名或指定新的 group/cluster，路由据此重选。自动更新查询要求活动事务。之后委托具体 Session 的 select/page/group/count，最后执行 after 并在 finally 恢复选库作用域。递归关联查询受路由深度限制。

**查询缓存与代理的位置：** 缓存读取、Key/TTL 处理、并发回源锁位于 `AbstractSession.getCacheValue`，不是 RouteSession。缓存未命中时，Session 执行得到 IDataBuffer，再由本 Session 的 CoderManager 解码；select/group 随后调用 `enhanceQueryResults`。缓存保存代理增强前的实体结果；缓存路径返回前复制对象，再增强关联与代理，不缓存事务绑定的代理。事务内查询和行锁查询绕过全局缓存，CACHE_ONLY 在这些场景拒绝执行。分页由 Session 分别 count 和 select，各自有缓存与实际执行边界。

**多缓存选择边界：** CacheCoreAutoConfiguration 收集 QueryCache Bean，创建唯一 CacheRegistry，并绑定 yulinlin.cache.default。无实现/无默认使用 NoOp；单实现自动选中；多实现必须指定默认，显式名称不存在及重名均报错。三个 Provider 的固定名称是 caffeine/ehcache/redis，无 group 配置。RouteSession、JDBC/ES/Mongo 工厂统一注入 registry.defaultCache，保证查询和失效使用同一实现；请求、Wrapper、JoinCache 不携带缓存选择参数，ORM 写后失效不广播其他实现。

RoutingCacheClient 仅管理缓存选择与只读清单：getCache()、getCache(name)、defaultName()、contains(name)、names()、caches()。每个实现复用一个 DefaultCache（实现 Cache），提供业务读写、泛型回源、批量操作和清理；默认与显式选择同一实现共享缓存对象及加载锁。业务 namespace 与 ORM namespace 始终隔离。Cache.clear(namespace) / clear() 不调用 ORM invalidateAll，也不清其他缓存或 Redis 整库。批量方法默认循环复用 Provider，不保证原子性，不新增线程/队列。无 Provider 时默认返回空缓存，ORM 直查数据库。注册表和客户端不接管 Provider 关闭生命周期；Redis 自带 L1 不作为独立 Provider 注册。公共 TTL 配置由各实现复用，配置只在启动时选择，不提供运行时热切换默认缓存。

CacheClient 不提供 ORM 表/实体清理入口，不依赖 ORM 注解解析或路由桥接。查询读写仍由具体 Session 完成，普通业务写入后的缓存失效仍由 RouteSession 协调事务提交；内部 CacheNamespaceResolver 和分区失效协议保留。需要刷新查询时通过 CacheMode.REFRESH，不使用业务缓存的 clear 操作代替。

**立即写入：** `RouteSession.executeNow` 没有外层事务时自动包装一次框架事务；有外层事务则直接登记参与者，不重复增加业务事务深度。先解析失效范围，再调用 Session.insert/update/delete，执行成功登记待失效范围并调用 after。最外层提交时才完成连接提交和缓存失效。`after()` 是“执行后”，不是“提交后”；需要提交成功通知时用 TransactionUtil.afterCommit。

**延迟写入：** before 在入队前执行并固定所选 Session；queue() 不允许在活动事务内使用，成功接收返回 0，不表示落库成功。WriteQueueManager 根据 Session **实例** + RequestType + fromClass 合并节点；同一 Session 内分组依次执行，不同 Session 受全局并发上限控制。当前活跃队列的节点总数达到 flush-size（默认 1024）可提前唤醒刷新，不是必须每组都满。后台执行回到 RouteSession.executeNow，各组独立事务；不重新执行 before。它不会把多次 +1 自动合为 +N，不保证跨分组的原请求顺序，也不是持久化消息队列。

**批量与事务：** AbstractSession 根据 batch()、执行器和 supportsParallelWrites 决定是否拆执行分组；具体 JDBC Session 再控制 executeBatchSize。executeBatch 是发送批次，不是提交事务。SQLite 禁止多连接写入拆组。业务自行开异步线程不会自动继承 TransactionContext；框架并行写入有自己的资源交接路径，不应直接复制为任意异步事务传播。

**统计聚合插入：** common 的 EntityCounter.insert 不进入 WriteQueueManager，而与原计数更新共用 EntityCounterManager 的定时刷新。RouteSession.resolveWriteGroup 在提交线程固定目标组，CounterInsert 缓存字段元数据，把数字转成不可变数值快照，非数字字段名/toString 构成维度，null 忽略。同组数字合并先完整校验，再原子替换行快照，溢出不能部分累加。刷新切换活动区后才通过 ModelInsertWrapper 触发 insertBefore，避免自动 ID/时间提前成为维度。每个数据源/实体分组批量插入、不主动拆多连接；失败批次保留已生成请求，不回并新窗口。标量编码器位于 core/coder；JdbcScalarTypes 仅提供原子类到基础存储类型映射，各数据库 SchemaManager 仍决定方言。内存窗口与失败队列都不持久化，不能据此承诺自然分钟对齐或 exactly-once。

**模型计数更新：** EntityCounter.update(model) 由 CounterUpdate 的 ClassValue 元数据识别唯一主键和可更新字段，终结时固定主键/数字快照，忽略非数字及零值。CounterNumbers 负责更新/插入共用的不可变数字转换，模型更新与链式更新统一以 BigDecimal 增量进入同一按组/实体/主键聚合区；同一行同步合并，整份新值计算完成后才替换。入队先解析实际数据源组，后台不依赖调用线程选库上下文。执行时通过空 IUpdateWrapper 仅生成 inc/dec 和主键条件，不走实体更新工厂，不触发 updateBefore/default 字段覆盖，再交 RouteSession 完成事务、解析、日志和缓存处理。失败增量恢复到活动区；不能承诺提交结果不确定时恰好一次。

**算术参数边界：** EntityCounter 链式 inc(x) 表示加 x、dec(x) 表示减 x，都接受正负整数、小数及现有原子数字类型。每次调用通过 CounterNumbers.snapshot 固定 BigDecimal 快照，拒绝 null/非有限浮点数/不支持的 Number 类型；Builder 和聚合器均使用 BigDecimal 合并，不再先转 long，dec 在 BigDecimal 上取负。终结时复制增量 Map，抵消为零不生成字段更新。输出参数能精确表示为 long 时保持整数，否则保留 BigDecimal；最终范围、精度由目标数据库列决定。JDBC UpdateFieldsParse 对 inc/dec 的数字使用 IParamsContext.putNumberGetKey，SimpParamsContext 保存原生数字、SqlParamsContext 负责委托，防止 BigDecimal 存储编码变成字符串后无法执行 PostgreSQL 数字加减。普通存储字段仍走原编码器，不改变表结构和数字文本存储约定；目标列必须能进行算术运算。

**事务与 sync 代理：** TransactionListenerManager 的线程上下文统一保存 depth、rollbackOnly、参与 Session、选库绑定、代理修改、缓存失效和 afterCommitTasks。嵌套提交只减深度，内层回滚标记整体 rollback-only。代理 setter 只记录修改，最外层提交前 flush，随后各参与 Session 提交自己的资源。清理旧上下文后才运行成功回调。多库/多连接是本地协调，不是 XA；已经提交的参与者不能因后续参与者失败而被保证回滚。ES/MongoDB 的资源参与标记不等于服务端原子事务。

## Session 日志与执行监听

已移除 `LogManager`、`LogPrint` 及其 Bean 注册，不再通过泛型反射识别请求并分发日志。当前调用链：

```text
AbstractSession 完成一次执行并固定耗时
  → 具体 Session.printExecution(event)
      → JDBC: JdbcExecutionLog.print(event)
      → ES: EsExecutionLog.print(event, logEnabled)
      → MongoDB: MongoExecutionLog.print(event, logEnabled)
  → 依次调用可选 SessionExecutionListener.afterExecution(event)
      → monitor 的 MonitorExecutionListener 识别 JDBC SqlNode 并记录
```

`SessionExecution` 与 `SessionExecutionListener` 位于 `com.yulinlin.data.core.session`。事件包含 session、requests、elapsedNanos、affectedRows、error、batch；elapsedMillis() 从同一纳秒值换算。batch 显式区分查询与写执行分组，单条写入或失败批次也属于 batch，不能用 requests.size() > 1 或 affectedRows 是否为 null 推断。affectedRows 只在成功写入时提供，其余为 null；error 为 null 只说明本次执行成功，不说明事务最终提交。txId、来源类和操作类型沿用 ParseResult 元数据。

计时边界保持在现有执行包装处：查询包含 beforeExecute、借连接、执行和读取 IDataBuffer，不含节点解析、实体解码、关联增强及日志/监听器时间；写入以 executeUpdate 分组计时，并行分组可能包含等待执行器调度的时间。一个分组内部可以执行多个 SQL 模板和多次 JDBC executeBatch，不应将它宣传成“每次驱动 executeBatch 的服务端纯 SQL 耗时”。

| 场景 | 通知规则 |
| --- | --- |
| select/count/group 实际访问数据源 | 每次执行一次，成功或失败都通知 |
| 分页 | count、select 分别通知；缓存命中的部分不通知 |
| 批量写入 | 每个 executeUpdate 分组一次，不给每行重复分配整批耗时 |
| 延迟写入 | 入队不通知，后台实际执行时通知 |
| 缓存命中、只解析节点、空写入 | 不产生数据库执行事件 |
| 提交/回滚 | 仍使用 TransactionLog，不冒充查询执行事件 |
| 启动 Schema DDL | 保留 Session 的独立 DDL 日志，不纳入当前执行监听 |

日志格式由 Session 直接委托普通辅助类，无日志 Bean。JDBC 保留各 Session 的 log、log-params、max-param-length、slow-sql-threshold、txId 与批量摘要规则；ES/MongoDB 从自身 SessionProperties 读取 log，失败仍输出异常。不要在工作线程通过 SessionUtil.route().session() 重新猜来源。

JDBC SQL 日志的展示键统一中文（事务ID、数据源、节点、操作、总耗时、操作数量、影响行数、SQL模板数、SQL、参数），内部 ParseResult.transactionId 和监控字段不改名。成功批次按 elapsedNanos 计算平均每条耗时，毫秒三位小数、固定小数点；分母用操作节点数而非影响行数，空批次不计算，失败不展示平均值与影响行数。总耗时沿用整数毫秒显示，低于 1ms 时可显示 0ms，但平均值仍从纳秒换算。参数展示仍受开关和截断限制，批量取首条参数，不改成全量输出。只有实际输出日志时才格式化平均值。SQL 文本采集规则需迁移，监控不依赖日志文本，无需改接口字段。

SQL 日志在同一个日志事件中换行展示摘要、SQL、参数，不拆成三次 logger 调用。SQL 和参数值内部仍规范化为单行并保留截断限制，只有框架添加展示换行；关闭 log-params 不输出参数行。采集文本日志的平台需按日志头配置多行合并，monitor 仍读取执行事件，不解析控制台文本。

JdbcSessionFactory、ElasticSearchFactory、MongoFactory 通过 ObjectProvider 收集排序后的监听器，在 create 时调用 `setExecutionListeners`。没有实现时为空列表，Session 不依赖 monitor 启动；关闭 SQL 日志不会关闭监控。当前内置 monitor 只消费 SqlNode，ES/MongoDB 不自动成为 SQL 监控数据；其他监听器可自己识别类型。

监听器扩展示例（方法体片段，放在业务或扩展模块的 @Configuration 中）：

```java
@Bean
public com.yulinlin.data.core.session.SessionExecutionListener executionListener() {
    return event -> {
        if (event.error() != null) {
            // 将需要的只读摘要交给自己的诊断系统，不在这里修改请求或提交事务。
        }
    };
}
```

监听器在执行完成线程同步调用，批量时可能并发；实现须线程安全、轻量，不持有请求级共享状态。requests 是只读列表快照，但其 ParseResult 不是深度不可变对象，禁止修改，不长期持有 Session、参数或异常引用；需要异步处理先提取必要摘要。日志辅助类和每个监听器的 RuntimeException 分别隔离，一处失败不跳过后续监听器，也不改变业务执行结果；不吞 JVM 致命 Error。

迁移时删除自定义 LogManager 注入和 setLogManager 调用；原 LogPrint 实现改成 SessionExecutionListener 或 Session 的 printExecution 覆盖。旧 SqlNodeLog Bean 替换不再生效；如需改变打印策略，覆盖 Session 方法。core、jdbc、ES/MongoDB 和 monitor 应一起更新，不能混用旧接口的二进制制品。此次只做静态检查，未编译或运行测试。

## 过滤器边界

查询与写入共用 PreparedRequest，携带最终 Request、Session 和真实入栈次数，不再用 Request.sessionChange 猜测清理次数。before 的新请求必须被采用，继承调用者路由/执行选项，同时检查 group 和 cluster。动态表名改写在 SQL 解析和缓存之前完成，fromClass 不必改变。具体 Session 的 `setFilterManager/getFilterManager` 已移除，第三方工厂也应停止配置这项依赖。

after 的新结果必须返回给调用方，按列表、Page、Integer 校验类型；IRequestFilter 对分页列表分发 selectAfter，仅更换列表时才创建保留 total/extra 的新 Page。缓存命中也执行 after，Session 内部分页调用不重复增强。延迟写 before 在入队前执行，after 在后台实际执行后触发，普通后台后处理异常不重试已执行 Node。完整规则见第二专题的[过滤器](02-CRUD与统计分析.md#请求与结果增强过滤器)。

SimpFilterManager 注册时复制并稳定排序，Comparator.comparingInt 避免 order 相减溢出；发布 volatile 数组快照，before/after 各自读取快照，无读锁、不创建迭代器。test 每次执行，不缓存依赖当前请求或用户的匹配结果。注册可与请求并发，但过滤器本身须无请求级共享状态。回归用例统一放在 admin/src/test/java，当前只做静态核对，未执行编译或测试。

## 事务上下文与提交扩展点

`TransactionListener` 保留 `startTransaction()`、`commitTransaction()`、`rollbackTransaction()`、`afterCompletion()`，`afterCommit()` 使用默认空实现保持接口兼容。监听器只接收最外层的生命周期通知：嵌套开启、提交不重复调用监听器，内层回滚只标记共享事务 rollback-only，直到最外层结束再通知。扩展监听器无需自行维护嵌套栈。`TransactionListenerManager.afterCommit()` 通知所有固定监听器，一处失败不会跳过后续监听器。

`core.transaction.TransactionContext` 只由 `TransactionListenerManager` 的当前线程存储创建、释放，不再使用 Session 私有的 TransactionScope 或上下文继承体系。RouteSession 及其注解入口复用它，嵌套只增减 `depth`；选定节点、参与 Session、按 Provider 汇总的缓存失效范围、`afterCommitTasks` 和代理 `ProxyChanges` 都在同一个上下文中。第一次创建它的管理器负责本次监听生命周期，后续路由嵌套不重复通知。不同线程隔离；各 JDBC Session 的事务连接资源仍单独持有，统一上下文不代表共用一个物理连接。已移除空转发层 BaseTransactionSession，业务事务转发直接位于 RouteSession，RegisterSession 只提供注册和选库钩子。

管理器最外层提交统一执行：固定监听器的提交前处理 → `ProxyChanges.flush()` → 各参与 Session 的资源提交 → 清理代理、解绑上下文并通知 `afterCompletion()` → 处理缓存失效 → 成功监听和业务回调。代理按来源组和实体类型分批生成部分更新，保留脏字段、主键和乐观锁逻辑；只迁移事务归属，不重写 CGLIB 或更新解析器。代理服务不再作为固定 TransactionListener Bean 重复注册，旧手动生命周期方法仅保留为弃用兼容入口。回滚丢弃脏记录和成功回调。提交资源出现异常时只做基本回滚和清理、向外报告异常，不实现断线确认、重试、补偿或分布式原子提交。

`TransactionUtil.afterCommit(Runnable)` 直接委托当前路由业务上下文的管理器，无业务事务直接报错，不提供独立 Session 或其他 Spring 事务管理器的回调兜底。业务 Runnable 保存在本次上下文，不放入全局 Listener 列表。`@Transactional` 使用 Spring 标准注解拦截器，经 `RouteTransactionManager` 接入 RouteSession，不另外注册拦截同一注解的切面。代理写回、固定提交前监听、连接提交和成功通知都由框架管理器按顺序执行；不注册 Spring 同步回调，不维护 `springStatus`，已经解绑的旧上下文不会清理后来新事务的状态。

清理异常不会跳过已成功提交事务的通知，某个监听器或业务回调失败也不会跳过后续任务；最终传播首个异常，其他异常合并为 suppressed，不重新进入已提交事务的回滚分支。所有显式开启必须配对结束；普通 CRUD 只登记资源，不增加深度。该能力不实现 REQUIRES_NEW、NESTED 或跨线程事务传播。业务用法见第二专题的[提交成功回调](02-CRUD与统计分析.md#提交成功回调)。

数据源实现的 `startTransaction/commitTransaction/rollbackTransaction` 仅负责本 Session 的连接资源；管理器首次登记时调用 start，最外层结束时调用 commit 或 rollback，不能反向调用管理器。`isOpenTransaction/setRollbackOnly/isRollbackOnly` 同样只读写本地资源状态。已删除重复的 `*TransactionResource` 桥接接口，不需要再实现两套同义方法。AbstractSession 的执行包装只记录日志、传播异常并标记自身资源失败，不自动开启或提交业务事务；JDBC 资源缺失的写操作明确报错，不能退化为自动提交。非 JDBC 默认只记录参与和回滚标记，保证事务内绕过缓存，不代表 ES/MongoDB 已具备服务端物理事务或回滚能力。

事务上下文、代理状态和独立连接管理的改动仅做静态核对，未执行编译、测试或打包。JDBC 资源登记仍延迟到真正执行 SQL 时才借连接，批处理连接在原线程初始化后再交给工作线程。

事务诊断开关为 `yulinlin.data.transaction-log`，默认关闭，由 core 自动配置传给 `TransactionListenerManager`。每个 `TransactionContext` 在创建时固定自己的 `TransactionLog` 和进程内事务 ID；JDBC 事务资源只捕获这一日志对象用于关联 ID，不通过它开启或协调业务事务。异步连接日志复用捕获的对象，SQL 执行前在所属线程将 ID 写入本次 `ParseResult`，包括并行解析后的所有批次，不读取工作线程的业务 ThreadLocal。关闭时仍保留 ID，但不读取事务诊断时钟、不输出生命周期日志；不存在框架事务时使用 `none`。日志不能改变提交/回滚决策；框架资源方法返回与 JDBC 物理 commit 分别记录，不把上下文清理、SQL 执行成功或 afterCommit 回调异常误报为数据库提交/回滚结果。该诊断改动仅做静态阅读核对，未编译、运行测试或打包。

`JdbcTransactionResources` 统一使用目标 `DataSource.getConnection()`，不调用 `DataSourceUtils`，不检查或复用 Spring holder。`TransactionAwareDataSourceProxy` 解包后再借连接，避免自管连接被代理重新导向线程绑定连接。具体借还和收尾规则见下节。

`jdbc.transaction.RouteTransactionManager` 只实现 Spring `PlatformTransactionManager` 协议，不继承 `AbstractPlatformTransactionManager`，不建立第二份资源上下文。每个注解调用的状态只保存原框架上下文身份和嵌套深度，用于防止跨线程、重复结束或手动事务未配对。Spring 标准拦截器负责注解解析和异常回滚规则，框架负责物理生命周期。仅接受 REQUIRED、默认隔离/超时和 readOnly=false，其他语义在业务执行前拒绝。DataJdbcApplication 提前注册 `@Primary` 的 `yulinlinTransactionManager`，使 Boot 默认 JDBC 事务管理器退让；通过 ObjectProvider 延迟获取 RouteSession，避免基础设施创建时循环依赖。原生 JdbcTemplate/MyBatis/JPA、其他事务管理器与本框架事务独立；不提供 Spring 同步事件或 JPA/JTA/XA 桥接。

源码入口：core/session、core/loadbalan、core/proxy、core/parse、core/coder；jdbc/session 和 jdbc/sql。缓存公共协议位于 cache-core，ORM 相关解析仍位于 core/cache，三个 Provider 只依赖 cache-core。为保持已有业务源码兼容，cache-core 中的公开类型暂时继续使用 `com.yulinlin.data.core.cache` 包名；模块边界已经独立，不要求调用方修改 import。数据库语法放在 Parse，驱动读写差异放在 Session，不额外引入 SqlDialect 或 Session.sqlXXX 拼接层。

## JDBC 事务连接资源

`JdbcTransactionResources` 由 `AbstractJdbcSession` 按事务持有，替代旧 `ConnectionPool`。真正的全局连接池仍是 Hikari、Druid 等 DataSource。业务只使用 RouteSession / 框架事务入口，不直接调用此资源类。

### 借用与并行批处理

1. 登记 Session 时只创建资源对象；第一次执行 SQL 前，在所属线程同步借入首条连接。首条连接获取失败向调用者传播，不允许本事务继续重试初始化。
2. 框架批处理线程捕获同一个资源对象，不复制业务事务 ThreadLocal。每条连接同一时刻只交给一个执行者；归还后可复用，重复归还或归还外部连接直接报错。
3. 全部已有连接繁忙、且未达到 `parallel-connections` 上限时，用虚拟线程申请额外连接。每个资源对象最多一个正在等待 DataSource 的扩容请求，不为每个等待者启动线程。
4. 等待执行者同时等待“已有连接归还”或“新连接加入”。即使扩容卡在 DataSource.getConnection，归还的连接也能立刻用于下一批，不必等扩容成功。
5. 额外借连接出现 SQLException 时，本事务停止继续扩容并复用已有连接，不因未执行 SQL 的可选扩容失败回滚已有业务。首条连接失败、业务 SQL 失败和物理提交失败仍正常传播；扩容的非 SQL 异常标记事务失败。

默认并行上限仍为 4，SQLite 仍为 1。Hikari 的池容量上限修正在资源类统一计算；其他 DataSource 以配置值为上限。这个值不是预留连接数，也不保证每个事务都能取得这么多连接。

旧模式下，两个事务各持有一条连接，又同时等待从已满的全局池借第二条，可能一直等到获取连接超时：执行完的连接只回到了各自事务，没有回到全局池。现在扩容等待与批处理执行分离，批处理可以用已归还的本事务连接继续执行并提交。它不解决数据库行锁冲突，也不使多连接共享隔离快照。

### 完成与释放

| 状态 | 允许行为 |
| --- | --- |
| ACTIVE | 借还连接、按需扩容、记录 rollback-only |
| FINISHING | 拒绝新借用；允许在用连接归还；不再接收扩容连接 |
| CLOSED | 连接已完成清理；重复 finish 不重复提交，不能重新初始化 |

进入 FINISHING 时唤醒等待者并中断尚未取得连接的扩容线程，但只等待正在执行业务的连接归还，不等待扩容结束。不能把仍在执行 SQL 的连接强行关闭，也不能为了缩短等待而提前提交。

驱动可能忽略中断：扩容线程晚到的连接不加入事务、不执行 SQL，单独回滚空事务、恢复原自动提交状态并关闭。必须给实际 DataSource 配置有限的获取连接超时；此实现不承诺能强制终止不响应中断、又没有超时的驱动调用。晚到连接的释放失败只能记录诊断，不能反向改变已经结束的业务事务。

所有已加入的连接统一逐个提交或回滚，始终尝试释放全部连接。提交失败时尝试回滚该连接及尚未提交的连接，首个异常向外传播，其他异常合并 suppressed；完成失败时不把 autoCommit 改为 true，避免意外提交。连接关闭成功与否不改变“已经提交的其他连接不能保证回滚”的本地协调边界。

已移除无人调用的 `ConnectionUtil` 旧事务入口及其第二套 ThreadLocal，也移除了旧 `ConnectionPool` 类型和 `getJdbcConnection/getConnections/isSpringManaged/clear` 兼容方法。外部若直接依赖这些内部接口，需要迁移；普通 Wrapper、RouteSession、`@Transactional` 和配置用法不变。

回归用例位于 [admin/JdbcTransactionResourcesTest](../admin/src/test/java/com/yulinlin/admin/jdbc/JdbcTransactionResourcesTest.java)，覆盖双事务扩容等待、已有连接复用、晚到连接关闭、收尾拒绝借用和提交失败清理。本次仅编写用例并静态核对，未编译或运行。

## 维护与 AI 检查清单

1. 先识别改动属于入口编排、公共执行流程、事务生命周期、节点解析、类型转换还是数据库资源；不要将所有逻辑堆到 RouteSession。
2. 同时查看查询、count、分页、立即写入、queue 和并行批次是否经过改动入口，避免只修单一路径。
3. before 必须先于 SQL/缓存 Key 生成；after 不等于 afterCommit，事务回调不能由日志或监控代替。
4. 查询缓存发生在代理增强之前；提交前 flush 代理，提交后处理缓存失效；不得缓存或跨线程复用事务代理。
5. 具体 Session 不得反向协调业务事务；它只管理自己的连接/客户端资源。工厂应完整初始化依赖，路由注册不负责补齐。
6. 数据库专属语法放 Parse，类型转换放本模块 CoderManager/ICoder，驱动绑定/读取放 Session；公共转换工具可复用，不让一个数据库规则影响其他数据库。
7. 日志在 Session 中直接调用辅助类，可选监听器只观察执行事件。日志级别不能控制 monitor 是否收集，日志文本变更不能改变监控接口字段。
8. Session、解析器、编码器与监听器通常被多请求共享；请求参数、别名、事务状态不能放入这些组件的普通实例字段。
9. 统一 API 不代表统一后端能力：多库本地协调不是 XA，非 JDBC 不自动获得回滚能力，批处理不是提交，内存延迟队列不是可靠消息系统。
10. 默认只允许源码/文档编辑与静态阅读检查。未经当前任务明确授权，不编译、打包、运行测试/JMH、Spring YAML 绑定测试或 git diff --check；测试代码若需新增统一放 admin/src/test。

### 日志类命名与迁移

三个普通日志辅助类统一命名为：
