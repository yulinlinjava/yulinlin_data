# 深度克隆性能对比报告

测试日期：2026-10-01。本报告来自本机实际 JMH 运行，不引用不同机器的第三方跑分。

## 结论

在本数据集上，自研 ReflectionUtil 的性能介于 Kryo 和 Java 序列化克隆之间。没有证据支持“比主流开源深克隆工具都快”。

- 逐条克隆：自研 193.88 ms，Kryo 103.98 ms。自研耗时是 Kryo 的约 1.86 倍；Kryo 耗时降低约 46.4%。
- 整体克隆：自研 411.11 ms，Kryo 241.60 ms。自研耗时是 Kryo 的约 1.70 倍。
- 相对 Apache SerializationUtils：自研逐条快约 10.89 倍，整体快约 1.46 倍。
- 自研逐条每批分配约 215.91 MiB，Kryo 约 66.38 MiB；自研约为其 3.25 倍，分配量是值得继续优化的方向。
- 手写基线最快，但只处理固定模型，不具备通用反射工具的适用范围。

## 环境与方法

| 项目 | 配置 |
| --- | --- |
| CPU | Intel Core i7-13700HX，16 核、24 逻辑处理器 |
| 系统 | Windows 11 家庭版中文版 |
| 系统可见内存 | 24,851,960 KiB，约 23.7 GiB |
| JVM | OpenJDK 25，25+36-3489 |
| JVM 参数 | `-Xms1g -Xmx1g`，未指定垃圾收集器，未启用 Debug |
| JMH | 1.37，AverageTime，单线程，2 个独立 fork |
| 预热 | 每个 fork 3 轮，每轮目标 2 秒 |
| 测量 | 每个 fork 5 轮，每轮目标 2 秒，共 10 个测量样本/方法 |
| 数据量 | 每次操作深克隆 200,000 个 User |
| 工具版本 | Kryo 5.6.2；Commons Lang 3.17.0 |

模型包含 long、boolean、String、Address、List<String>、Map<String,Object>、int[]。Map 中的 address 与 User.address 指向同一地址对象。不同用户没有共享可变对象。为支持序列化，User 和 Address 实现 Serializable。

Kryo 按线程复用实例，关闭强制注册要求，开启 copyReferences，使用默认序列化器。自研仍每次调用创建独立 DeepCopies。手写实现对当前全部可变字段创建副本，并保留地址别名关系。它不支持任意字段扩展或任意循环图。

各组 setup 中检查小样本的字段值、可变字段对象独立性及地址共享关系；小样本 smoke run 和全部正式 fork 均通过。数据构造和检查不计入正式计时，结果返回给 JMH 消费。本次未执行整个项目的单元测试或 Spring 集成测试。

## 测量结果

误差列为 JMH 输出的 Error，不是标准差；默认对应 99.9% 置信区间半宽。单对象耗时为批量平均值除以 200,000，不是孤立调用的延迟。

| 方法 | 每批平均耗时 ± Error（ms） | 单对象摊销耗时（μs） | 每批分配（MiB） |
| --- | ---: | ---: | ---: |
| 手写逐条 `manualPerUser` | 19.501 ± 1.355 | 0.098 | 60.27 |
| Kryo 逐条 `kryoPerUser` | 103.977 ± 7.306 | 0.520 | 66.38 |
| 自研逐条 `perUser` | 193.878 ± 21.813 | 0.969 | 215.91 |
| Kryo 整体 `kryoWholeList` | 241.603 ± 12.687 | 1.208 | 100.33 |
| 自研整体 `wholeList` | 411.107 ± 38.755 | 2.056 | 187.33 |
| Apache 整体 `serializationWholeList` | 599.324 ± 94.892 | 2.997 | 335.11 |
| Apache 逐条 `serializationPerUser` | 2110.918 ± 70.763 | 10.555 | 2607.72 |

分配量是累计分配，不是存活堆或峰值内存，因此 1 GiB 堆下，一次操作累计分配超过 1 GiB 并不矛盾。

不能按 GC 总次数或总时间直接判定谁更好：JMH 按时间测量，快的方法会执行更多批次。手写虽然 GC 次数最多，但单批分配最低且耗时最短。比较单批分配优先看 gc.alloc.rate.norm；gc.alloc.rate 高也不等于效率低。

## 公平性与限制

1. 优先比较相同粒度：逐条对逐条，整体对整体。逐条克隆不能保留跨用户的可变对象共享关系，整体图克隆可以；本数据集没有这类跨用户引用。
2. 自研和 Kryo 可复用不可变字符串，序列化可能重新构造字符串；这是机制差异。本检查要求值相同、可变对象独立及地址别名保留，不要求字符串实例相同。
3. 手写是当前模型的专用基线，不是任意对象图的通用替代品。
4. 当前没有测试 records、无默认构造器类型、不同容器实现、跨用户循环图或多线程场景。结论不可扩展为完整功能兼容性排名。
5. 本次无 CPU/分配热点采样，无法将差距精确归因于某一函数。更少的分配、复用上下文、容器和字段访问策略都是后续分析方向，不是已经证明的根因。
6. 使用个人工作机器，没有 CPU 绑核或控制其他应用负载。两个 fork 仍不等于多次独立实验。进一步优化前应延长测量，并重复整组测试。
7. Kryo 依赖 ReflectASM（本次为 1.11.9），但本次只把它作为 admin 基准依赖，没有恢复 lang 的 ASM 方案。是否接受生产引入它是另一个选型问题。

## 复现与文件

基准：`admin/src/main/java/com/yulinlin/admin/DeepCloneBenchmark.java`。

本次实际执行：

```powershell
# 先进行小样本校验
./admin/run-clone-benchmark.ps1 -Size 10 -Forks 1 -Warmups 0 -Iterations 1 -Duration 100ms -ResultName smoke

# 正式比较，默认 20 万条、2 fork、3 轮预热、5 轮测量、每轮 2 秒
./admin/run-clone-benchmark.ps1
```

脚本使用 E:/maven 本地缓存和已有 lang/target/classes 辅助类，显式重新编译当前 HandleAccess、ValueCopies、DeepCopies、ReflectionUtil 和基准，输出目录置于运行类路径最前面，避免误测旧 ReflectionUtil。它不依赖可执行 Maven，不下载依赖、不启动 Spring、不连接数据库。此次编译与 JMH 均成功；没有验证 Maven 全模块打包。

原始结果：

- `admin/target/clone-jmh/deep-clone-comparison.json`
- `admin/target/clone-jmh/deep-clone-comparison.log`

原始文件位于 target，执行 clean 会清除；本报告保留了本次核心结果。JMH 关于 Unsafe 的弃用警告未导致失败。

建议：保留自研工具的既有兼容语义，先定位其分配热点；对极高频且模型固定的路径可以考虑专用手写映射。如果考虑采用 Kryo，应补充业务对象兼容性测试，不能仅凭本报告直接整体替换。
